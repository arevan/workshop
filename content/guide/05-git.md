Git — система, которая запоминает состояния проекта, чтобы можно было вернуться назад. Учить её не нужно: всю работу делает агент, тебе хватит двух фраз. Но один раз её надо поставить и настроить — это десять минут.

## Две фразы

**«Сделай коммит»** — сохранить текущее рабочее состояние. Говори каждый раз, когда что-то заработало и тебе это нравится. Перед крупной правкой — тоже.

**«Откатись к прошлому коммиту»** — вернуть проект к последнему сохранённому состоянию. Говори, когда после правки стало хуже, а агент не чинит это за пару попыток.

Коммит — твоя рабочая точка. Пока её нет, каждая правка агента — риск: сломает работающий экран, и вернуть будет нечего. С коммитами цикл спокойный: заработало → коммит → пробуем дальше → не вышло → откат. Экспериментировать не страшно.

На хакатоне сделай коммит сразу, как основной сценарий начал проходиться от начала до конца. Даже если дальше всё пойдёт не так, останется то, что можно сдать.

## Установка и настройка

**Проверь, есть ли git.** На Mac он обычно уже стоит вместе с Xcode. Открой терминал и выполни:

```
git --version
```

Если версия не показалась, macOS сама предложит доустановить инструменты разработчика — согласись. На Windows скачай с [git-scm.com](https://git-scm.com) и ставь, ничего не меняя.

**Представься один раз.** Git подписывает каждый коммит — без этого он будет ругаться:

```
git config --global user.name "Имя Фамилия"
git config --global user.email "почта@example.com"
```

Для рабочих проектов ставь рабочую почту — ту же, что во внутреннем репозитории.

Всё. Дальше команды набирать не придётся: агент делает это сам.

## Репозиторий на сайте

Пока проект живёт только на твоём компьютере, git — это история правок и кнопка «отменить». Если добавить репозиторий на сайте, появляется ещё три вещи: резервная копия, доступ к коду с другого компьютера и возможность показать проект коллеге ссылкой.

Что где хранить:

- **Учебные демки без данных** — можно на GitHub, в том числе публично
- **Всё, что связано с работой** — только внутренний репозиторий компании
- **Сомневаешься** — оставь локально, ничего не потеряешь

> Публичный GitHub для кода банка закрыт. Это не формальность: код, попавший в публичный репозиторий, считается утёкшим, даже если удалить его через минуту — он успевает разойтись по зеркалам и поисковым индексам. То же касается демок со скриншотами боевых экранов, внутренними ссылками или доступами внутри.

## Как привязать проект к сайту

Порядок одинаковый для GitHub и для внутреннего GitLab:

1. Создай пустой репозиторий на сайте: кнопка **New repository** (в GitLab — **New project → Create blank project**). Название любое, README и .gitignore добавлять не нужно — они уже есть в проекте
2. Скопируй адрес репозитория, он показан сразу после создания
3. Вернись к агенту и скажи: «привяжи проект к этому репозиторию и запушь: <вставь адрес>»
4. Дальше — фраза **«запушь изменения»**, когда хочешь обновить копию на сайте

Первый раз git попросит авторизоваться. На GitHub откроется окно браузера — войди под своим аккаунтом. Во внутреннем GitLab обычно нужен токен доступа: он создаётся в настройках профиля на самом сайте, и его вставляют вместо пароля.

> Токен — это пароль. Не вставляй его в чат с агентом и не сохраняй в файлах проекта: git запомнит его сам после первого ввода.

## Что видно на сайте

**История коммитов** — список всех сохранённых состояний с датами. Можно открыть любое и посмотреть, что именно менялось: удобно, когда пытаешься понять, после какой правки всё сломалось.

**Файлы проекта** — можно читать код прямо в браузере, в том числе с телефона.

**Ссылка на проект** — то, чем делятся с коллегой вместо архива.

## Что делать не нужно

Разбираться в ветках, merge и pull request. Для демок хватает линейной истории коммитов. Понадобится работать в команде над одним проектом — тогда и разберёшься, а агент к тому моменту объяснит на твоём же коде.
